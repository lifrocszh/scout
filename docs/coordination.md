# Distributed crawl coordination

Workers advertise free task capacity by issuing a held `ClaimOne` RPC. The coordinator assigns a durable task lease when work becomes eligible and replies to that call. A worker asks once for each HTTP request permit; if policy prevents an immediate grant, the coordinator queues the request and holds the reply until a real grant is available. These held unary RPCs provide capacity credits without a separate streaming transport.

The dispatcher wakes after scheduling-relevant mutations, cancellation and calculated eligibility deadlines. It considers ready work centrally rather than requiring workers to retry task claims every 250 ms or request permission every 25 ms. It rechecks eligibility in the durable grant transaction; if policy changes since the readiness query, it retains the waiter and retries. Pending reply queues are bounded. Robots refresh ownership still uses its existing `Waiting` response and worker polling; this change does not remove that separate coordination mechanism.


Deadline wakeups cover task retries, all task lease expiries (including quota-satisfied Sources), origin or shared-group spacing, active permit expiry, queued request lease expiry and the run duration. The dispatcher captures PostgreSQL time before checking readiness, so a deadline crossing during that pass causes an immediate recheck. Grant transactions can remove other expired queue rows; the dispatcher resolves their held replies before arming its next timer.
PostgreSQL remains authoritative for task leases, request budgets, global and per-origin concurrency, start spacing, robots policy and result fencing. The coordinator persists assignments and grants before replying. A queued permit is bound to its task lease and is extended with a valid lease renewal. Stale lease epochs cannot obtain fresh grants or submit accepted results. On cancellation, disconnected queued replies are removed and their waits are cancelled; an already granted request remains reserved until its report or safe expiration because a dropped RPC does not prove HTTP stopped. On coordinator restart, pending request waits are cleared because their RPC connections have vanished; active permits remain reserved until report or expiry. Durable unfinished task work remains recoverable.

Workers reject grants that arrive without enough remaining permit lifetime for the configured HTTP timeout and a safety margin. This check compares expiry timestamps across coordinator and worker clocks, so multi-host deployments require synchronized clocks. Dropping a task or rejecting its lease renewal aborts its spawned HTTP task instead of leaving it running independently.

The notification contract uses protocol version 3. Coordinator and workers must be upgraded together; the version handshake rejects incompatible binaries. `Waiting` responses for task claims and request permits are no longer part of the version 3 worker contract.

HTTP budgets remain configurable crawl policy. Public sites retain suitable per-origin concurrency and spacing regardless of worker count. Owned capacity fixtures can use higher bounded limits and zero spacing to measure coordination capacity without an artificial HTTP ceiling. A focused low-cap fixture workload separately measures the cost of policy waiting.

Result intake uses a bounded set of PostgreSQL lanes, configured by `SCOUT_COMPLETION_LANES` (2–8, default 4). Each lane owns one connection and a queue of seven jobs. Queue reservations are bounded by message count and bytes; the dispatcher limits outstanding task credits to eight per result lane and pauses assignments when result capacity falls behind. It resumes after a result drains. Validation, body write/fsync, PostgreSQL acceptance, SQLite projection and quota checks run outside the coordinator core lock. Completion acknowledgement still waits for durable body storage, the fenced PostgreSQL transaction and SQLite projection. SQLite remains derived and is rebuilt from accepted PostgreSQL results after a crash.

Page-only results do not lock the fair-scheduling cursor because they admit no new frontier work. Results with discoveries retain the scheduler-row lock across frontier-capacity counting and atomic discovery insertion; sitemap admission uses the same durable lock. Task uniqueness, Source-scoped content groups, fair claim order and lease fencing remain database-enforced. The scheduler still has one PostgreSQL connection and its own core lock; this change parallelizes result intake while keeping scheduling policy centralized. Robots refresh waiting still polls. Measurements must report scheduler row-lock waits separately from result transaction time, and count network RPCs separately from internal dispatcher passes.
